# Развёртывание и GitHub Pages

Публичный экземпляр Altioris работает на VPS с Node.js и SQLite. [Открыть демо](https://31-77-222-138.sslip.io/).

## Почему целиком на Pages не работает

[GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) раздаёт статические HTML, CSS, JavaScript и ресурсы. Он не запускает HTTP-сервер Node.js и не предоставляет процессу постоянный SQLite-диск.

| Возможность Altioris | Один GitHub Pages | Сервер с Node.js и постоянным диском |
| --- | --- | --- |
| Изображения, CSS, шрифты | Да | Да |
| Вход и серверные сессии | Нет | Да |
| Заявки и сохранение диалогов | Нет | Да |
| Частные PDF и проверка владельца | Нет | Да |
| Рейтинг по серверным данным | Нет | Да |
| Будущие LLM-вызовы с закрытым API-ключом | Нет | Да, после интеграции |

Интерфейс обращается к `/api/...` на своём origin, а сервер обслуживает маршруты приложения. Публикация `public/` не создаёт работающую демонстрацию. Копирование SQLite или ключей в статические ресурсы раскрывает их посетителям.

Статический интерфейс и внешний API технически возможны, но потребуют переработки путей `/altioris/`, SPA-маршрутов, API-адреса, CORS, cookies и CSRF-проверок. Этот режим не настроен. Для сохранения функций проще обслуживать интерфейс и API с одного HTTPS-домена.

## Серверная конфигурация

Используйте Node.js 24+ на VPS или платформе с долгоживущим Node-процессом и постоянным локальным диском. HTTPS завершается на обратном прокси. Для одной SQLite-базы начинайте с одного экземпляра приложения; несколько машин потребуют отдельного решения для БД и ограничений входа.

1. Клонируйте проект и задайте постоянные пароли по README. Инициализируйте SQLite в доверенной среде с помощью `npm run dev` и перенесите согласованную копию заполненной базы. Для публичного запуска с хэшами в базе нужны все 13 аккаунтов.
2. Подготовьте каталог постоянного диска с доступом только сервисному пользователю. Настройте согласованное резервное копирование SQLite с учётом WAL и проверьте восстановление.
3. Создайте игнорируемый `runtime/.env` по примеру ниже, заменив домен и пути.
4. Запускайте `npm start` под менеджером процессов и направьте HTTPS-прокси на Node.js. `npm run dev` принудительно использует loopback и предназначен для разработки.

```dotenv
NODE_ENV=production
HOST=127.0.0.1
PORT=3000
ALTIORIS_ORIGIN=https://students.example.org
ALTIORIS_DB=/srv/altioris-data/altioris.sqlite
ALTIORIS_AUTH_SOURCE=sqlite
```

Если платформа требует привязку к `0.0.0.0`, задайте `HOST=0.0.0.0` и закрывайте внутренний порт средствами платформы. `ALTIORIS_ORIGIN` — точный публичный HTTPS-origin без пути. В production сессионная cookie получает флаг Secure. При `ALTIORIS_AUTH_SOURCE=sqlite` удалите `ALTIORIS_ACCOUNTS_FILE` и переменные паролей из окружения приложения. При запуске сервер проверяет наличие хэшей всех 13 аккаунтов и использует существующие записи.

Для обновления существующего VPS, установленного с `altioris.service` и базой в `/var/lib/altioris-campus`, выполните из корня проекта `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\update-vps-auth.ps1 -VpsIp <IPv4>`. Скрипт проверяет хэши действующих паролей, делает резервную копию SQLite, обновляет сервис и проверяет два входа. После успешной проверки он удаляет старый файл открытых паролей с VPS. Локальный список для выдачи тестовых аккаунтов хранится отдельно.

Пакет интерфейса публикуется командой `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\update-vps-ui.ps1 -VpsIp <IPv4>`. Скрипт сверяет опубликованные файлы через HTTPS и при ошибке возвращает предыдущую версию. Для обновления окна поддержки и серверных ответов добавьте `-IncludeSupport`. В этом режиме скрипт перезапускает Altioris с прежней SQLite.

По умолчанию используется текущее время. `ALTIORIS_CLOCK=demo` фиксирует дату на 23 ноября 2026 для воспроизводимой демонстрации. Учебные даты покрывают 2025/26 и 2026/27. Миграция базы до версии 3 удаляет только исходные примеры предыдущей версии. Заявки студентов, пользовательские фотографии и сессии сохраняются.

## Проверка публикации

Проверьте вход по HTTPS, неверный пароль, выход, заявку, свой PDF, переписку и восстановление данных после перезапуска. Убедитесь, что `/runtime/`, `.env` и база недоступны через прокси, а два аккаунта не видят частные записи друг друга.

Ограничение входа работает в памяти процесса и видит адрес соединения с прокси. Для публичного сервера настройте дополнительные лимиты на прокси, мониторинг и резервное копирование. Административный процесс обработки заявок, сброс пароля и живые операторы пока не реализованы.

## Будущий умный помощник

LLM-ключ хранится в серверных секретах. Сервер сам выбирает разрешённые записи текущего пользователя, ограничивает запросы и время ожидания, обрабатывает недоступность модели. Изменения выполняются через проверенные функции, а не по произвольному SQL из ответа модели. LLM не отменяет необходимость сервера.

Порядок проверки изменений и публикации описан в [инструкции выпуска](release.md).
